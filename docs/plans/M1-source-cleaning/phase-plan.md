# M1 원본 정제 — 단계 상세 계획서

- 상태: 진행 중
- 작성일: 2026-09-28
- 승인: 2026-09-28
- 상위 문서: `docs/plans/00-master-plan.md` 7장 M1

## 1. 목적

- 원본 파일 10개를 읽어 화면(M2)이 바로 쓸 수 있는 정제 테이블(parquet)로 만듦. DART 없이 파일만으로 진행함
- 이름 결합으로 정보보호 공시 제조사 387곳에 공정위·배출권·공장 정보를 붙이고, 헷갈리는 결합은 검수 목록으로 뽑음
- `python -m pipeline.jobs.annual` 한 번으로 원본에서 정제 결과까지 다시 만들 수 있게 함 (연 1회 갱신의 기반)
- 결과가 기획 단계 점검 수치와 같은지 회귀 테스트로 고정하고, GitHub CI에서 테스트가 자동으로 돌게 함

## 3. 범위

포함
- 원본 읽기 기반: manifest로 원본 찾기·무결성 확인·manifest 재생성 명령, 공통 정제 함수
- 원본별 정제: KISA 2개년, 공정위 2종, 배출권, 전국 등록공장
- 이름 결합과 대응표(xwalk), 사람이 고치는 덮어쓰기 파일, 검수 목록
- 회사 요약 테이블(후보 목록·필터용)과 신호 태그 중 DART 없이 계산되는 것
- 출처·기준일 테이블(`source_meta`), 검증 게이트, 개인정보 차단 검사
- CI(`ci.yml`), 문서 갱신(`data-schema.md` 실제 테이블, `CLAUDE.md` 명령)

제외 (다른 단계에서 함)
- DART 호출, corp_code 부여, 공장 결합의 본사 주소 확인 → M3
- 매출 기반 지표(IT 투자/매출), 동종업계 벤치마크(`peers.py`) → M4
- 최근 90일 공시 신호 → M5
- 산단공 시도별 통계 4종 정제 → 보류. M2 디자인에서 지역 맥락 정보가 필요하다고 정해지면 그때 함
- 화면 → M2

## 4. 핵심 설계

임시 회사 식별자
- M1에서는 corp_code가 없으므로 `company_id` = KISA 2026 기업명의 이름키(정규화한 이름)로 둠. 2026 파일은 정규화 후 중복이 0이라 식별자로 쓸 수 있음
- 모든 테이블은 `company_id` 열로 이어지고, 앱(M2)도 `company_id`만 씀. M3에서 `build.py` 한 곳에서 값을 corp_code로 바꾸면 앱은 고칠 필요가 없음

테이블 (`data/processed/`, 커밋함)

| 테이블 | 한 행 | 행 수(예상) | 내용 |
|---|---|---|---|
| `kisa_disclosure` | 회사 × 공시연도 | 1,599 (773 + 826) | KISA 전 열 정제본. 금액(원), 인력, O/X → 참거짓, 인증 목록, `attachment_only`, 업종 대분류 |
| `company` | 대상 회사 | 387 | 후보 목록·필터용 요약. 규모 구간, IT 투자액·증감률, IT 인력 비중, 보안 지표, 세부업종, 상장 여부, 기업집단, 계열 SI 유무, 배출권, 공장 수·시도 목록, 신호 태그 |
| `group_membership` | 회사 × 소속 집단 | 3,539 | 공정위 소속회사 정제본. 개인정보 3개 열 제거. 금액은 원 단위(백만원 × 10⁶), 개별 기준 표시 |
| `business_group` | 기업집단 | 102 | 집단 순위·규모, 계열 SI 회사 목록 |
| `emission_target` | 배출권 업체 | 772 | 업체코드, 업체명, KSIC 5자리·중분류 |
| `factory` | 공장 | 대상 회사와 이름이 맞는 공장만 (수천 행 예상) | 단지명, 산업단지 입주 여부, 생산품, 시도, 시군구, 동명 의심 표시 |
| `xwalk` | 원본 이름 1개 | 수백 행 | 원본, 원본 이름, 이름키, company_id, 결합 방식, 상태(확정·검수 필요·실패) |
| `source_meta` | 원본 | 7 | 출처, 기준일, 행 수, 빌드 시각(build_id) |

- 금액은 모두 원 단위로 저장하고 열 이름에 `_krw`를 붙임. 억원 표시는 앱이 함
- 공장은 21만 행 전체를 커밋하지 않음. 전국 이름별 공장 수·시도 수는 빌드 때 계산해 동명 판단에만 씀
- 법인등록번호는 M3 결합 확인용으로 `data/cache/ftc_jurir.parquet`(gitignore)에만 씀

손으로 고치는 파일 (`data/manual/`, 커밋함)
- `xwalk_overrides.csv`: 원본, 원본 이름, company_id(또는 NONE), 사유. 자동 결합보다 항상 우선함
- `si_manual.csv`: 업종코드로 잡히지 않는 계열 SI 보완. 기업집단명, 회사명, 사유

검수 목록
- `data/processed/review_queue.csv`: 사람이 볼 목록. 한글이라 GitHub에서 바로 읽힘
  - 동명 의심 공장
  - KISA 업종 결측
  - 2025↔2026 이름 불일치
  - 덮어쓰기 파일과 충돌하는 결합

결합 규칙 (M1 범위)
- 이름키 완전 일치만 씀. 비슷한 이름 추정(유사도 매칭)은 하지 않음 → 놓친 결합은 검수·덮어쓰기로 보완하고, M3에서 DART로 다시 확인함
- 공장: 이름이 맞은 공장은 결합하되 동명 의심 표시를 붙임. 의심 기준은 회사 이름 하나에 공장 20곳 이상인 경우로 시작함 (대원산업 58, 태광산업 31 등). 본사 주소 확인은 M3에서 함

신호 태그 (M1에서 계산하는 것)
- IT 투자 +20%, CISO 겸직, 외부 보안인력, 인증 없음, 계열 SI 없음, 배출권 할당대상, 2개 이상 시도
- "인증 없음" = 인증 칸에서 알려진 인증(ISMS, ISMS-P, ISO 27001, ISO 27701, PCI-DSS, CSAP 등)을 하나도 찾지 못한 경우
- 최근 90일 공시는 M5에서 추가함

작업별 요점
- T1.1
  - M0의 일회성 manifest 스크립트를 `python -m pipeline.manifest refresh`로 옮김
  - 정제 함수는 원본 없이 도는 표 형식 테스트로 검증함 (CI에서도 돎)
- T1.2
  - 투자·인력 수치가 공시연도의 전년 실적인지 KISA 공시 안내로 확인함 (M4의 IT 투자/매출에서 매출 연도를 맞추는 데 필요)
  - 확인하지 못하면 확인하지 못했다고 기록함
- T1.3
  - 대표자·사업자등록번호는 읽은 직후 버림
  - 법인등록번호는 processed에 넣지 않고 로컬 캐시에만 씀
- T1.5
  - 21만 행을 읽는 데 걸리는 시간을 재서 기록함 (연간 빌드 시간의 대부분)
- T1.6
  - 결합 수 회귀 테스트는 원본이 있을 때만 돌고, CI에서는 건너뜀
- T1.7
  - 검증 게이트: 키 고유성, 필수 열, 행 수 급감(20% 초과) 차단, 개인정보 열·13자리 숫자 없음
  - 게이트를 통과해야 파일을 씀

## 6. 완료 기준

| 기준 | 확인 방법 |
|---|---|
| 원본에서 정제 결과까지 한 번에 만들어짐 | `python -m pipeline.jobs.annual` 실행 → `data/processed/` 테이블 8개 생성, 검증 게이트 통과 |
| 결과가 기획 단계 점검 수치와 같음 | 회귀 테스트 통과: 대상 387, 증감 계산 351, 이름 일치 공정위 125·배출권 142·공장 334, 계열 SI 49개사·37개 집단, 배출권 772, 소속회사 3,539행 |
| 정제 함수가 원본 없이 검증됨 | 표 형식 단위 테스트 통과 (원본 없는 환경에서도 돎) |
| 개인정보가 결과물에 없음 | processed 파일에 대표자·법인등록번호·사업자등록번호 열이 없고 13자리 숫자 값이 없음 (테스트), 푸시 전 `git grep` 점검 결과 없음 |
| 검수할 것이 목록으로 나옴 | `review_queue.csv` 생성, 항목별 건수를 결과에 기록함 |
| GitHub에서 테스트가 자동으로 돎 | CI 통과 (원본 필요한 테스트는 건너뜀) |
| 문서가 실제와 맞음 | `data-schema.md`에 M1 테이블·열 정의, `CLAUDE.md`에 빌드·manifest 명령 |

## 7. 위험과 대응

| 위험 | 대응 |
|---|---|
| 이름키 완전 일치로는 표기 차이(한글 음차·영문, 오타)를 놓침 | 놓친 건수를 결과에 기록하고 덮어쓰기 파일로 보완함. M3에서 DART로 다시 결합함 |
| 공장 동명 오결합이 화면에 그대로 나감 | 동명 의심 표시를 테이블에 넣고, M2 화면에서 "동명 회사가 섞였을 수 있음"을 보이게 함. 확정은 M3 |
| M3에서 corp_code로 바꿀 때 앱과 테이블이 깨짐 | 앱은 `company_id`만 쓰고, 값 교체는 `build.py` 한 곳에서만 하도록 설계함 |
| KISA 수치의 기준 연도가 불명확해 M4 비율이 어긋남 | T1.2에서 확인하고, 확인 전까지 IT 투자/매출은 만들지 않음 (M4 범위) |
| 21만 행 공장 파일 처리로 빌드가 느림 | 시간을 재서 기록하고, 필요하면 이름별 통계를 로컬 캐시로 둠 |
| pandas 3 동작 차이(`str` dtype, copy-on-write)로 조용한 오류 | 테스트에서 dtype을 명시해 확인하고, 연쇄 할당을 쓰지 않음 |
| 정제 결과 parquet이 커져 저장소가 무거워짐 | 공장은 이름 일치분만 저장함. 테이블별 크기를 결과에 기록함 |
| 원본이 없는 CI에서 테스트 대부분이 건너뛰어져 의미가 줄어듦 | 정제 함수는 원본 없이 도는 가짜 데이터 테스트로 따로 검증함 |
